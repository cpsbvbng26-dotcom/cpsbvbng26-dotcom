# 正本の優先順位

同じ内容が複数の場所にあるとき、**どれを正とするか**を固定します。
新しい順位を作るのではなく、**すでにそう運用しているもの**を書き留めるだけです。

## 種類ごとの正本

| 対象 | 正本 | 理由 |
|---|---|---|
| **論文の PDF と書誌** | **Zenodo** | DOI が付き、版が固定される。GitHub 上の PDF は同じものの控え |
| **実装と版管理** | **GitHub** | 履歴・差分・CI がある。Zenodo のアーカイブは特定時点の写し |
| **著者の識別子** | **ORCID** `0009-0000-1406-0547` | 同姓同名と区別できる唯一の識別子 |
| **公開の入口** | **GitHub Pages** `https://cpsbvbng26-dotcom.github.io/cpsbvbng26-dotcom/` | 核の主張・撤回・全成果への導線が一枚にある |
| **撤回と正誤** | **`trinity-infinity/ERRATA.md`** | 何が撤回されたかは、ここだけが正 |

## 縄張りは README にある

**城の縄張り図は、この repo の README が持っている**。十のリポジトリと
その外側を、城の部位に当てて並べてある —— 天守閣・本丸・石垣・出丸・
武具蔵・作事方・二の丸・三の丸、そして堀・狭間・物見櫓・番所・大手門・
搦手・虎口・高札場・検地帳・城絵図・検分状。

**ここで同じ語を、別のものに当てない**。この文書は README が言うところの
`城絵図` である。**絵図が縄張りと食い違えば、絵図のほうが誤りである。**

**2026年9月17日、実際に食い違わせた**。外のプロフィール頁を `本丸` と呼び、
`天守`・`石垣`・`大手門` も README と別のものに当てていた。
README では `本丸` は `trinity-infinity`、`石垣` は `self-correction` である。
**六つのプロフィール頁は、README の図では `飛び地・陣屋` に当たる。**
そちらの語に直した。

## 同じ人物について、別の媒体に別の記述があるとき

**大谷恒について、GitHub の外にも記述があると外部の点検が述べている**（Google Sites の家系図。
`docs/external-evaluations.md` の九件目）。**その媒体は作業環境から開けないので、内容は確かめていない。**

| 対象 | 正 | 理由 |
| --- | --- | --- |
| **1943年9月11日時点の階級・受章・假記番号** | **史料ノート**（`10.5281/zenodo.22055709`） | 原資料（JACAR `C12070491000`）に当たって書いてある |
| **最終階級・乗艦・配置** | **どこも正ではない** | 公報だけでは確定できないと、そのノート自身が書いている |
| 続柄 | 先祖の公的記録の頁 | 根拠を文書・証言・未確認に分けてある |

**階級が二つ出てくることは、それ自体では矛盾ではない**。公報が記録しているのは、その日の階級である。
のちの昇進を否定しない。**問題は事実ではなく確度である** —— こちらが「確定できない」と書いていることを、
別の媒体で確定して書けば、**同じ著者が二つの基準を使っていることになる。**

**揃え方は一つしかない**。別の媒体の断定に、それを支える別の出典を付けるか、断定をやめるかである。
**こちらの記述を、確度の低いほうへ合わせることはしない。**

## Zenodo との連携についての但書

**Zenodo を正としていますが、この連携は自動ではありません。**
上の表を「仕組みで保証されている」と読まれると誤ります。実際にどこまで保証されて
いるかを、ここに書き出します。

### 1. この作業環境から Zenodo へは、何も送れません

Zenodo には、GitHub の Release を拾って版を固定し DOI を付ける連携があります。
**この作業環境からは、その入口に触れられません**。タグの push が 403 で通らないため、
Release を作れないからです。

Zenodo への登録も、新しい版の作成も、**すべて著者が手で行っています。**
この環境がしているのは、受け取った番号を書き写すことだけです。

### 2. 番号は転記であって、確認ではありません

`zenodo.org` にも `doi.org` にも DataCite にも、この環境からは届きません。
外向きに出られるのは GitHub だけです。

**番号が実在しないと言っているのではありません**。登録したのは著者本人です。
番号は Zenodo が発行したものを、著者が読み取って渡しています。
**存在は著者の証言で立っています**。登録簿が根拠を「紙面」と「証言」に分けて
どちらも数えているのと、同じ扱いです。

確かめられないのは、その先です。

| 疑っていないこと | 確かめられないこと |
|---|---|
| 番号が Zenodo で発行されたこと | ここに書き写した文字列が、その番号と一字一句同じか |
| 著者がそれを読み取ったこと | その番号が、指すつもりのレコードを指しているか |

**起きる誤りは、存在ではなく書き写しのほうです。**
`10.5281/zenodo.22335691` と `...692` の食い違いがその例で、六箇所が `692`、
一箇所だけが `691` です。書き写しの誤りか、概念 DOI と版 DOI の違いかは、
レコードを開かなければ決まりません（次の節）。決まらないものは「未確認」と
書いてあります（[doi-index.md](doi-index.md)）。

### 3. 版の DOI か、概念 DOI かも、判別できません

Zenodo は、全版を代表する DOI（concept DOI）と、その版だけを指す DOI（version DOI）
を別に発行します。**一覧にある番号がどちらなのかは、この環境からは分かりません。**
Zenodo のレコードを開かなければ判別できないからです。

「最新版を指したい」場合に使うべき番号は、この一覧からは選べません。
`10.5281/zenodo.22335691` を未確認のまま置いてあるのは、まさにこの区別が
付かないためです。

### 4. 食い違ったときは Zenodo が正です

書誌、ライセンス表示、版の日付。GitHub 側の記載と Zenodo 側の設定が食い違った
場合は、**Zenodo を正としてください**。GitHub 上の PDF は控えです。

これは `trinity-infinity/README.md` にある注記と同じ扱いです。

### 5. 新しい版を作っても、ここの PDF は変わりません

Zenodo で新しい版を作ることと、このリポジトリの PDF を差し替えることは、
別の操作です。**公開済みの PDF は改変も再生成もしません。**
誤りが見つかったときに直すのは、PDF ではなく `ERRATA.md` のほうです。

逆も同じで、ここで正誤表を直しても Zenodo 側のレコードは変わりません。

### 6. Release が無いことは、何も意味しません

タグの push が 403 で通らないため、**この環境から Release を作った実績はありません。**
GitHub に Release が並んでいないことから、Zenodo の登録状況を推測しないでください。

### 7. この環境がしないこと

| | |
|---|---|
| **番号を推測して埋めない** | 受け取った番号だけを書きます |
| **Release を勝手に作らない** | Zenodo での公開と版の作成は著者の操作です |
| **タグを push しない** | 通らないだけでなく、勝手に版を切らないためでもあります |

## 外部からの評価が付く先

外部の公開レビューの場が受け付けたのは **SSRN の DOI** だけでした。Zenodo の DOI は
対象外です。つまり「引用は Zenodo で」と固定している一方で、**第三者の評価は
SSRN 側にしか残りません**。片方だけを見た読者は、もう片方に気づきません。

SSRN 版があるのは四篇です。**Trinity-Infinity の Series I と III、Fragmentarian は、
この経路では評価を受けられません**。Series I と III は出したまま結果を待っており、
Fragmentarian は弾かれています。

記録は [external-evaluations.md](external-evaluations.md) にあります。

## 陣屋は六つある —— 特性ごとに一つ

**陣屋と正本は別のものである**。ここを混ぜると、どちらの規則も効かなくなる。

| | 何を決めるか | どこ |
| --- | --- | --- |
| **正本** | **写しが食い違ったとき、どちらが勝つか** | 論文は Zenodo、識別子は ORCID、実装は GitHub、撤回は `ERRATA.md` |
| **陣屋** | **人を探しに来た者が、どこに着くか** | 下の六つ |

**Zenodo は陣屋ではない**。プロフィールの頁を持たないためである。論文の正本では
あるが、**そこに着いても人は出てこない**。番号と PDF が出てくる。

**陣屋は特性ごとに一つずつ置く**。六つを一つに寄せない。読者の来る道が六本あり、
**どの道から来ても陣屋に着くようにするほうが、一つを陣屋と決めて残りを門にするより
壊れにくい。**

| 特性 | 陣屋 | 運営 | 性格 |
| --- | --- | --- | --- |
| **国内** | **researchmap** | **JST**（科学技術振興機構）が提供、**NII**（国立情報学研究所）が研究開発 | 国の機関 |
| **欧州** | **CV HAL** `cv.hal.science/nemoto-takuya` | **CCSD**（Centre pour la communication scientifique directe）—— **CNRS** の一部門 | 国の機関 |
| **哲学分野** | **PhilPeople** | **PhilPapers Foundation** と、Western University の **Centre for Digital Philosophy** | **学界の非営利。国の機関ではない**。購読で自立している |
| **英語圏の社会科学** | **SSRN** | **Elsevier**。2016年5月に買収 | **営利企業。国の機関ではない** |
| **引用の索引** | **Google Scholar** | **Google**。2004年11月20日に公開。Google は 2015年から Alphabet Inc. の完全子会社 | **営利企業。国の機関ではない** |
| **平易な説明** | **Kudos** | **Kudos Innovations Ltd**（英国オックスフォード。2013年設立） | **営利企業。国の機関ではない** |

**運営の三行は `検索で確認（原典未読）` である**。`researchmap.jp`・`hal.science`・
`philpeople.org` のいずれにも作業環境から届かない。**公式の記載そのものは読んでいない。**

**六つのうち三つは営利企業が持っている**。SSRN と Google Scholar と Kudos である。

**そしてその三つはいずれも、同じ手が計測も持っている。**

| 陣屋 | 同じ手が持つ計測 |
| --- | --- |
| SSRN（Elsevier） | **PlumX**（Elsevier） |
| Google Scholar（Google） | **被引用数**（Google Scholar 自身が数える） |
| Kudos（Kudos Innovations） | **共有の経路と閲覧の数**（Kudos 自身が数える） |

**陣屋と計測が同じ手にある**。三例ある。**そこは分けて読む。**
置いた先が数えているとき、数は独立した外部の目ではない。

**これは規則ではない**。営利であれば必ず数える、という話ではなく、
**いま並んでいる三つがそうだというだけである**。四つ目が出てきたときに
同じとは限らない。

**Kudos の欄には、他所の数も混ざる**。自分で数えているのは共有の経路と閲覧で、
**Altmetric の点数と被引用数は引いてきたものである**（前者は Altmetric、
後者は Crossref）。**同じ画面に並んでいても、出所が違う。**

**欧州の陣屋は CV HAL であって、HAL そのものではない**（利用者の指摘）。
**HAL は置き場で、CV HAL がその上に立つ面である**。両方とも CCSD が動かしているが、
**人を探しに来た者が着くのは面のほうである。**

**置き場と面を分けるのは、他の陣屋でも同じである。**

| 陣屋（面） | その下の置き場 |
| --- | --- |
| CV HAL | HAL |
| SSRN の著者頁 | SSRN |
| Google Scholar の著者頁 | Google Scholar の索引 |

**researchmap と PhilPeople と Kudos は、面と置き場が同じ一つである。**

HAL は 2001年に École normale supérieure で始まり、のちに CCSD へ移っている。
PhilPapers Foundation は David Bourget（Western）と David Chalmers（NYU・ANU）が
共同で運営している。**どちらも同じ等級である。**

### 六つとも写しである

**陣屋であることと、正本であることは両立しない**。六つの中身はいずれも
Zenodo と ORCID から写したものである。

**Google Scholar だけは、写し方が違う**。他の四つは中身をこちらが入れるが、
**Google Scholar が載せるものは向こうが集めてくる。**

**ただし「管理していない」は誤りである**。2026年9月17日に直した。
著者は一覧を自動更新にするか自分で確認するかを選べ、項目を足すことも
外すこともできる。**選べないのは、収集が何を見つけるかと、被引用数の数え方である。**

**SSRN だけは、全篇が揃っていない**。別の DOI が付いているのは四篇で、
二篇は出したまま結果を待っており、一篇は**弾かれている**
（Fragmentarian Spiritual Individualism。
[external-evaluations.md](external-evaluations.md)）。
**陣屋でありながら、そこだけを見た読者は全部を見ていないことになる。**

**researchmap の登録は、推薦ではなく審査を通ったものである** ——
HAL に登録したプレプリントを業績として出している（証言。
[external-evaluations.md](external-evaluations.md)）。
**ただし、その審査が見たのは登録の要件であって、論文の中身ではない。**

**食い違いが見つかったときは、Zenodo と ORCID に合わせて六つの側を直す。逆はしない。**
**陣屋だからといって、正本に勝つことはない。**

### 古い写しのままであることが分かりました

**2026年9月17日、利用者が Vercel 側にまだ古い版が出ていることを確かめました。**
`courses.json` を直して GitHub へ push したあと、GitHub Pages では新しい科目名が
出ているのに、`vercel.app` では前の科目名が残っていました。

**上の但し書きの後半が当たっていたことになります。**「GitHub と連携していれば追随し、
していなければ古い写しのままです」の、していない側です。

**こちらでは確かめていません**。`vercel.app` は作業環境から開けず、Vercel の API も
チームの一覧が空で返ります。**根拠は利用者の観察です**（`証言`）。

**入口が古い写しを出しています**。リポジトリの About → Website は `vercel.app` を
指しており、外から来た人が最初に見るのはそちらです。**いま出ているのは、
17 科目 34 単位になる前の版です。**

道は二つあります。

| | すること | 結果 |
| --- | --- | --- |
| 追随させる | Vercel のプロジェクトを GitHub と連携し直す | push のたびに新しくなります |
| 入口を移す | About → Website を `github.io` に変える | 正本がそのまま入口になります |

**どちらも利用者の手になります**。Vercel の設定にも GitHub の About にも、
この作業環境からは届きません。
